NAME

eem — Ephemeral Environment Manager for the current Bash shell

SYNOPSIS

source env-manager.sh

Requires Bash 4 or newer. Source the script in the shell whose environment you want to configure. Direct execution is refused because it cannot update the calling shell.

DESCRIPTION

EEM is an interactive menu for exporting temporary environment variables, grouped by application or system. It records each managed variable’s original value and export state so that deleting it can restore the previous shell state.

In an interactive terminal, the menu normally uses the alternate screen with centered, fixed-width frames. Exiting restores the original terminal screen. Source the script again to reopen the menu without discarding existing management records.

MENU

1. List variables
Show managed variables grouped by application. Secret values are masked; other values are displayed.
2. Add or update variables
Choose an application, naming mode, variable name, and whether the value is secret. Reuse an application name to add more variables. Replacing an existing managed value requires confirmation and retains its original restoration state. A name already managed under another application is refused.
3. Delete variables
Restore and stop managing one variable, an application’s variables, or all managed variables, after confirmation.
4. Launch OpenCode
Run the opencode executable found in the command search path. Return to the menu when it exits.
5. Launch Grok
Run the grok executable found in the command search path. Return to the menu when it exits.
E. Exit menu
Return to the current shell, keeping the exported variables active.

VARIABLE NAMING

The default and recommended choice is the original variable name. For example, group SLACK_BOT_TOKEN under Slack and OPENAI_API_KEY under OpenAI. Application grouping does not rename these variables unless you select prefixing.

The optional naming mode prepends EM_<APP>_ to the name you enter. The application name is uppercased, non-letter/non-digit/non-underscore characters become underscores, repeated underscores are collapsed, and leading or trailing underscores are removed. An empty normalized name becomes APP.

For example, entering BOT_TOKEN under Slack in prefixed mode produces EM_SLACK_BOT_TOKEN; entering API_KEY under OpenAI produces EM_OPENAI_API_KEY. Prefixing does not create an alias for the original name. Use it only when the consuming program accepts that exported name.

Variable names must match [A-Za-z_][A-Za-z0-9_]*: letters, digits, and underscores, without a leading digit. Application names must be nonempty and must not contain control characters.

SECRETS

Marking a value as secret hides terminal input and replaces its value with ******** in EEM listings. Nonsecret input is visible.

Masking is not encryption. Values remain ordinary shell variables exported to child processes. EEM writes neither entered values nor its management records to disk; it provides no persistent secret store. This does not prevent another program or the operating system from recording data.

RESERVED NAMES

EEM rejects shell-critical names affecting command lookup, loader behavior, shell startup, prompts, history, locale, terminal dimensions, and Bash execution state. Examples include PATH, LD_PRELOAD, BASH_ENV, PROMPT_COMMAND, LANG, and names matching LC_*.

Its own namespaces, _EM_*, _em_*, em_*, and env_manager, are also reserved. Arrays, read-only variables, and name references cannot be managed. Validation applies to the final exported name; an optional prefix can yield an allowed name without modifying the shell-critical variable itself.

RESTORING

On first managing a variable, EEM remembers whether it existed, its value, and whether it was exported. Subsequent updates preserve that original snapshot.

Deleting a managed variable restores its original value and export state, or unsets it if it did not previously exist. Application deletion and Delete All apply this restoration only to managed variables; unrelated variables are untouched.

Restoration refuses incompatible declarations, including arrays, read-only variables, and name references. Resolve the incompatible declaration before retrying; EEM does not write through a name reference.

LAUNCHING AGENTS

OpenCode and Grok do not need to be launched from the menu. Configure the environment, choose E. Exit menu, then start the agent in that same shell:

source env-manager.sh
# Configure variables, then choose E to exit the menu.
opencode
# Or, instead:
grok

Exiting the menu keeps the variables. The agent must be started in the same shell to inherit them; a separate terminal or an already-running agent does not receive those changes automatically.

Closing the shell clears its variables and EEM’s in-memory records. It does not revoke credentials or erase environment copies already inherited by running child processes. Likewise, restoring a variable in the shell does not change an existing child process’s environment.

SECURITY

Exports are session-wide, not restricted to the application group shown in the menu. Child processes inherit exported values, including secrets. Treat programs launched from this shell as trusted recipients and export only what they need.

EEM validates names and assigns values without eval. Display sanitization removes control characters without changing stored values, but is not a complete defense against misleading Unicode text.

The menu restores saved terminal settings and preserves existing interrupt and termination traps, using a plain interface when those traps are present. Abrupt shell termination can bypass normal menu cleanup.

EEM does not encrypt memory, securely wipe the Bash heap after deletion, hide process environments, or provide multi-user access control. Hidden input and masked listings reduce accidental display, not access by the current user or privileged software.
